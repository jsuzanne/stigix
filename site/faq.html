Frequently Asked Questions

Everything you need to know about Stigix — from traffic generation and security testing to IoT simulation and operations.

The Traffic Generator creates continuous background HTTP/HTTPS traffic to simulate realistic enterprise user activity across many SaaS applications such as Microsoft 365, Google Workspace, Zoom, and Salesforce.

Traffic Generation is meant to simulate user demand and application mix, while Security Testing is meant to validate whether security policies block or allow known test destinations.

Each application has a weight that defines its relative probability of being selected during traffic generation, so a higher-weight app appears more often over time.

Start with core productivity and collaboration apps such as Outlook, Teams, Google Workspace, Zoom, Slack, and Salesforce, then tune weights so business-critical apps dominate while secondary apps still appear naturally.

Yes. The Traffic Generator supports consumer-style profiles with social media, streaming, and gaming applications using heavier weights for those categories.

You can define targets by domain name or IP address. If you need plain HTTP instead of HTTPS you can specify the protocol explicitly in the application definition.

Use the dashboard statistics, traffic.log, and stats.json to compare the configured weights with the observed request distribution and success rates.

First check whether traffic generation is enabled, whether the correct network interface is configured, and whether the traffic generator container is running without errors.

Traffic Generation is ideal when you want to show realistic SaaS behavior, SD-WAN path steering, application visibility, and policy decisions under user-like load rather than just one-off probes.

Connectivity probes are lightweight tests that continuously check service reachability and responsiveness using methods such as HTTP, ICMP, DNS, and related synthetic checks.

The goal is to show whether critical services are actually healthy and responsive from the branch point of view — not just whether a path is technically up.

You can monitor internal applications, SaaS services, collaboration platforms, DNS resolution targets, and other endpoints defined in the connectivity configuration.

Traffic Generation creates ongoing application load, while Digital Experience monitoring measures health, reachability, and responsiveness of selected services.

It helps explain that "reachable" does not always mean "usable," especially when latency, instability, or intermittent degradation affects user experience.

Yes. Because the probes run continuously, they can expose intermittent problems and inconsistent service behavior that a single manual test may miss.

Pick a small set of business-relevant services — usually one or two SaaS apps, one internal dependency, and one generic internet target for comparison.

Security Testing validates URL filtering, DNS security, threat prevention behavior, and related policy enforcement using known test destinations and files.

For URL tests it evaluates HTTP outcomes; for DNS tests it checks whether malicious domains resolve or return NXDOMAIN; for threat tests it checks whether EICAR-style downloads succeed or fail.

This usually means the test traffic is not passing through Prisma Access or the required security policies are not configured in the active path.

No. Scheduled tests run automatically in the background after the configured interval. "Run All Enabled" is only for manual on-demand execution.

Manual execution works best for demos. For PoCs, 30–60 minute intervals are recommended. For lighter continuous monitoring, 60–120 minutes is appropriate.

Look for Blocked results in the results table and confirm that the statistics dashboard reflects enforcement over time.

Check that scheduling is enabled, the interval is valid, at least one test type is selected, and then inspect backend logs if the UI looks correct.

Security Testing is best when you want a clear proof point that policy enforcement is happening — especially for URL filtering, DNS security, and Threat Prevention validation.

IoT Simulation creates realistic device behavior on the wire using Scapy, including DHCP, ARP, and device-specific traffic patterns, so simulated devices look more like real endpoints to the network.

It is useful when the demo needs device visibility, segmentation, identification, or OT/IoT-specific behavior rather than only browser or SaaS application flows.

Multiple device families are supported: cameras, sensors, smart plugs, smart lighting, printers, HVAC-related devices, and industrial or medical profiles depending on the configuration.

DHCP fingerprints make the simulated devices more believable and help with identification workflows, including Palo Alto IoT Security classification scenarios.

Use the Python generator for fast, deterministic, offline output. Use the LLM-based method when you want a customer-specific or industry-specific device set for a tailored demo.

Voice Testing generates RTP-style traffic and measures metrics such as jitter, loss, latency, R-value, and MOS to assess voice quality under network conditions.

The Convergence Lab is used to measure failover behavior precisely, including blackout windows and directional loss during path changes or impairments.

It is designed as a measurement tool, not just a visual indicator, so it can quantify how long failover actually impacts traffic and how recovery behaves in each direction.

Because failover impact is not always symmetric, and one direction may recover differently from the other — which is especially relevant for voice and real-time traffic.

Use it when you want to show the practical user impact of latency, jitter, and packet loss rather than only bandwidth or reachability.

Use it when the customer wants proof of failover quality, precise recovery timing, or visibility into how path changes affect application continuity.

The all-in-one Stigix image is the recommended default deployment model. Legacy separated images remain available for advanced scenarios.

Check whether Docker is running, whether containers are up, whether port 8080 is available, and whether the web UI logs show startup or connectivity errors.

Verify that interfaces are configured correctly, confirm traffic generation is active in the dashboard, and inspect the traffic generator logs.

Use the documented maintenance flow: preserve configuration, pull the latest images, and restart cleanly so that settings and logs are not lost unnecessarily.

A strong JWT secret, changed admin credentials, HTTPS through a reverse proxy, firewall restrictions, resource limits, and log retention settings are all recommended controls.

The platform uses shared configuration and log volumes, including traffic logs, test results, and rolling statistics files that are read by the dashboard and backend.
